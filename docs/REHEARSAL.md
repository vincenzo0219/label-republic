# 오픈 리허설 기록 (Sprint 24)

오픈 전에 [RUNBOOK](RUNBOOK.md)을 처음부터 끝까지 그대로 따라 해 보고, 막힌 곳을 고친 기록입니다. 다음 리허설(분기마다 백업 검증, 1년에 한 번 새 서버 복구) 때 이 표와 비교하세요.

- 환경: 저장소를 새로 받은 빈 디렉터리, Docker Compose, `--profile https`(Caddy, `DOMAIN=labelrep.test`, `CADDY_TLS="tls internal"`), 워커 4개. 실제 도메인·인증서·휴대폰은 쓰지 않았습니다.
- 부하: 목록·글·검색·헬스 요청을 끊지 않고 계속 보내는 스크립트로, 각 훈련 동안의 실패 수와 가장 긴 대기 시간을 셌습니다.

## 1. 한 일과 결과

| 단계 | 한 일 | 결과 |
|---|---|---|
| 첫 배포 | `.env.example` → `.env`, `docker compose --profile https up --build -d` | 마이그레이션 001~023 적용, `/api/health` 200 (프록시 경유 HTTPS) |
| 시드 | `seed:curator` | 검수(`reviewedBy`) 안 된 시드는 게시하지 않고 개수를 알려 줌 — 검수한 파일은 커밋 후 이미지 재빌드가 필요 (F4) |
| 첫 백업 | `backup` 서비스 | 처음엔 마이그레이션 전에 돌아 실패 (F8) → 수정 후 앱 기동 10분 안에 백업 |
| 백업 검증 | `docker compose --profile ops run --rm restore verify …` | 체크섬·임시 DB 복원·행 수 일치 "검증 통과" |
| 무중단 업데이트 | 부하를 걸어 둔 채 새 이미지로 `up -d --build app` | 요청 **300건 중 실패 0**, 가장 긴 대기 **6초** (프록시가 최대 15초 붙잡고 기다림) |
| 롤백 | 023 스키마 위에 Sprint 22 이미지로 되돌림, 다시 앞으로 | 정상 — 추가된 컬럼·테이블은 옛 코드가 무시. 태그 방식(`prev`→`current`)도 확인 |
| 서버 통째 분실 | 볼륨까지 지우고 새로 → 백업 복사 → `restore` → 앱 기동 | health 200 까지 **12초** (작은 DB), 글·사진 복원 확인 |
| DB 재시작 | 부하 중 `docker compose restart db` | 수정 전: **워커가 모두 죽음** (F10). 수정 후: 중단 동안 API 500·health 503, 복귀 뒤 자동 재연결, 워커 재시작 0회, 실시간 댓글 다시 붙음 |
| 워커 강제 종료 | 부하 중 워커 0(배치 담당)을 `kill -9` | 1초 뒤 다시 뜸, 요청 **105건 중 실패 0**, 배치도 새 워커 0에서 계속 |
| 앱 프로세스 사망 | 컨테이너 주 프로세스 `kill -9` | Docker 가 **5초** 만에 다시 띄움 |
| `docker kill` | 컨테이너를 사람이 강제 종료 | 다시 띄우지 않음(Docker 규칙: 사람이 멈춘 것) → 프록시 502. `docker compose up -d app` 필요 — RUNBOOK 5장에 적음 |
| XFF 위조 | 프록시 경유로 `X-Forwarded-For` 를 바꿔 가며 추천 | 한 사람으로 묶여 중복 방지됨 (앱 포트를 직접 열지 않은 경우) |

## 2. 발견한 문제

| # | 문제 | 심각도 | 처리 |
|---|---|---|---|
| F1 | 앱 포트가 `0.0.0.0:3000` 에 열림 → `TRUST_PROXY=true` 이면 누구나 XFF 를 위조해 매 요청 다른 사람처럼 보일 수 있음 | 높음 | `127.0.0.1:3000` 으로만 공개 |
| F2 | RUNBOOK 은 "프록시 뒤라면"이라고만 하고 TLS 프록시 구성이 없음. `SITE_URL` 은 https 만 받으므로 프록시 없이는 운영 모드로 뜨지 않음 | 높음 | `deploy/Caddyfile` + `proxy` 서비스(`--profile https`), `.env` 의 `DOMAIN`·`ACME_EMAIL`·`CADDY_TLS` |
| F3 | Caddy 기본 설정이면 접속 기록에 방문자 IP 가 남음 → 개인정보처리방침("원본 IP 미저장")과 어긋남 | 중간 | 접속 기록을 켜지 않음 (오류·인증서 로그만) |
| F4 | 시드는 이미지 안에 들어가므로, 서버에서 검수 표시를 해도 반영되지 않음 | 낮음 | RUNBOOK 1장 10번에 "커밋 → 재빌드 → `docker compose exec app npm run seed:curator`" |
| F5 | `tls internal`(자체 인증서)이면 브라우저가 인증서를 믿지 않아 서비스 워커·오프라인·푸시가 동작하지 않음 | 낮음 | RUNBOOK 1장에 적음 — 이 기능들은 실제 도메인에서 확인 |
| F6 | 앱 이미지 851MB (Next 202MB 중 SWC 네이티브 93MB) | 낮음 | 그대로 둠 — SWC 는 실행 중에도 `next.config.ts` 를 읽는 데 필요. 이미 빌드 캐시·다른 플랫폼 바이너리는 뺌 |
| F7 | 이 리허설 환경(사내 프록시)에서만 `npm ci` 가 인증서 문제로 실패 | — | 환경 문제, 저장소 변경 없음 |
| F8 | 첫 백업이 마이그레이션 전에 돌아 실패 → 반쪽 파일(.dump 만)이 남고, 다음 시도까지 하루를 기다림. 반쪽 파일은 보관 개수 정리에도 걸리지 않아 쌓임 | 중간 | 마이그레이션 전이면 파일을 만들지 않고 건너뜀, 실패 시 이번 파일 삭제, 10분(`BACKUP_RETRY_SEC`) 뒤 재시도 |
| F9 | RUNBOOK 의 복구 명령(`npm run db:backup:verify`·`db:restore`)은 Node·pg 클라이언트가 필요한데, 앱 이미지엔 pg 클라이언트가, 서버엔 Node 가 없음 → 장애 때 쓸 수 없음 | 높음 | `scripts/restore.sh` + `restore` 서비스(`--profile ops`) |
| F10 | DB 재시작 때 쉬던 커넥션의 오류가 처리되지 않아 워커 프로세스가 모두 종료, 실시간 LISTEN 재연결 중에도 같은 문제 | 높음 | 풀 오류 처리(`src/lib/db.ts`), 끊긴 LISTEN 연결 정리(`server.ts`), 회귀 테스트 `tests/resilience.test.ts` (수정 전 실패·수정 후 통과 확인) |
| — | 롤백 절차가 "이전 이미지로 되돌림"뿐, 이전 이미지를 어떻게 찾는지 없음 | 중간 | `image: labelrep-app:current` 고정 이름 + 업데이트 전 `prev` 태그 (RUNBOOK 4장) |

## 3. 리허설로 확인하지 못한 것 (사람이 실제 환경에서)

- 실제 도메인의 Let's Encrypt 발급·갱신, 80·443 방화벽
- 실제 휴대폰에서 서비스 워커·오프라인 저장·푸시 알림
- 백업의 원격 복사(`rclone` 등)와 원격 사본에서의 복구
- 큰 DB(글 20만 건 이상)에서 서버 분실 복구 시간 — 참고치: 덤프 1분, 복원 2분
- 앞단에 CDN·로드밸런서를 더 둘 때의 `TRUST_PROXY_HOPS`

# 오픈 리허설 2차 (Sprint 34)

Sprint 24 이후 마이그레이션이 024~031 까지 늘었고(규칙 투표·리뉴얼·읽기 전용 모드·답글·브랜드 별칭 등), 1차는 작은 DB 로 했습니다. 이번에는 **운영 규모의 데이터가 쌓인 서버를 Sprint 24 코드에서 오늘 코드로 올리는 경우**를 그대로 해 봤습니다.

- 환경: Docker Compose `--profile https`(Caddy `labelrep.test`, `tls internal`), 워커 4개. Sprint 24 커밋(`03b371b`, 마이그레이션 023)으로 먼저 띄운 뒤 데이터를 채움.
- 데이터: 글 20만·댓글 58만·추천 350만·방문 기록 200만·제품 4만·제품 태그 13만·성분 값 26만, DB 3.9GB.
- 부하: 1차와 같은 스크립트(요청 4줄기, 홈·보드·글·검색·제품·브랜드·리뉴얼·health)를 업데이트·롤백·재업데이트·DB 중단 내내 계속 보냄.
